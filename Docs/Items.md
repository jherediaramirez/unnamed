# Items

The Playground's items: every block's item (601, from [Blocks](Blocks.md)), plus the 63 Tier A items of Minecraft Java 26.3 that are not a block's item: the 35 tools (pickaxe, axe, shovel, hoe and sword in wooden, stone, copper, iron, golden, diamond and netherite), the 7 spears, the 14 ore and tier materials, stick, bucket, water bucket, lava bucket, apple, bread and cooked beef; and, since loot step 2b, the 23 items the imported blocks' loot tables drop (the 9 saplings, wheat seeds, flint, snowball, clay ball, book, glowstone dust, cocoa beans, melon slice, gold nugget, prismarine crystals, sweet berries, glow berries, amethyst shard and resin clump; 86 in all). The ones that place a block in vanilla (the saplings, wheat seeds, cocoa beans, sweet berries and glow berries) are items only here: placing them is a later block step. They carry the 26.3 numbers: stack size, durability, attack totals, tool rules and wear. The research is [scout F's record](Records/2026-10-09-Items-Scout-Research.md); the plan and its decisions are [the items phase plan](Records/2026-10-09-Items-Phase-Plan.md).

## Data flow

| Step | What | Where |
|---|---|---|
| Reference | `items.json` (the 86 items' components, tags, creative positions, model definitions), `models.json`, `textures.json` (sprites and opacity masks), `tags.json`, `item_index.json` (all 1,658 ids), `lang.json` (the tooltip text), the break-time truth table, and two black-box facts files from the server jar's own `ItemStack` (`tools/ItemFacts.java`): the durability bar at every damage value and every item's tooltip lines. Since items S5b also the block loot tables (`loot_tables.json`, flattened from the jar's `loot_table/blocks/*.json`, and copies of those files and the two tool predicates; every imported block's since loot step 2a). Items added after an import are appended last (`APPEND_LAST`, loot step 2b), so no item, model or sprite layer moves. Generated, hash-listed, never edited. | `Reference/minecraft-items-26.3/` |
| Tags | The 53 vanilla item tags as `Item.*` gameplay tags (`enchantable/mining_loot` is `Item.Enchantable.MiningLoot`). | `Config/Tags/MinecraftItemTags.ini` (`ItemImportData.py --write-tags`) |
| Import | The 93 item sprites as GUI textures, the same sprites as texture array layers, and the registry asset. | `Scripts/Editor/ImportItems.py` → `/Game/Items` |
| Runtime | `UFoundationItemAssets::LoadDefault()` loads `DA_Items` once; `UFoundationInteractionSettings::BuildRules` turns its entries into item definitions. | `Source/Unnamed/Foundation/FoundationItemAssets.*` |

`/Game/Items` (`UUnnamedProjectSettings::ItemRoot`; Python `ProjectPaths.item_asset()`) is always cooked. It holds:

- `DA_Items` (`UFoundationItemAssets`): per item its id, name, protocol id, group, material and kind, max stack, max damage, attack totals and the attribute modifiers verbatim, the tool component (default speed, ordered rules, damage per block, can destroy blocks in creative), damage per hit, blocking disable time, enchantability, the repair selector and its items, `Item.*` tags, creative positions, model definition and sprite names. Also the 93 models' layers and display transforms (Mojang units, verbatim), the 93 sprites' sizes, opacity masks and array layers, the tooltip's lang keys, the block loot tables and the tool predicates their conditions name (items S5b), and the reference's SHA-256.
- `Gui/item/<sprite>` and `Gui/block/<sprite>` (the saplings' sprites are the jar's block textures): the 93 sprites with the creative screen's pixel settings (as `BlockRoot/Gui`). The hotbar and the creative screen draw an item's first texture from here.
- `M_HeldItem`: the held items' cutout material (`Scripts/Editor/CreateItemMaterials.py`, items S4; see "Presentation").
- `T_ItemTextures` (the 86 sprites of 16 x 16) and `T_ItemTextures32` (the spears' 7 in-hand sprites of 32 x 32): texture arrays for the held items (items S4), mip 0 only, nearest filtering. Each sprite's layer is in `DA_Items` (`FFoundationItemTextureAsset::Layer`). Vanilla's item mips are not measured; the project's mip generator is a port for block sprites.

`ImportItems.py` checks every reference file against `SHA256SUMS.txt` (the full verifier needs Pillow, which editor Python lacks). It verifies an existing `DA_Items` (the reference digest, the item ids, the model and texture counts) and refuses to replace it when the reference changed; a second run writes nothing. To reimport, move the old assets away deliberately, then restart the editor (the runtime loads `DA_Items` once per process). One exception, items S5b's loot migration: a `DA_Items` imported from the pre-loot reference (`ImportItems.PRE_LOOT_SHA256`), with the environment variable `UNNAMED_ITEMS_MIGRATE=loot` set, is verified as usual and then gets only the loot tables and the new digest, so the texture arrays and sprites stay as they are. The S5b rebuild of the reference left every other file byte-identical (the S5b record has the proof).

## Ids

- **Item ids** are saved ids: the 26.3 item names (`iron_pickaxe`, `stick`, `water_bucket`). A block's item has the block's id. Only `air` and `wheat` share a block's id in 26.3 without being that block's item (`item_index.json`); neither is an item here.
- **Retired, never reused:** `dummy_block_item` (blocks replaced it), `practice_pickaxe` and `practice_sword` (the 26.3 iron tools replaced them).

## The merge

`BuildRules` builds the authority's item list in this order:

1. Block items (`AddBlockItems`): one per block that has an item.
2. `DA_Items`, in registry order.
3. Project items (`UFoundationInteractionSettings::Items`, empty by default).

An id that is already defined logs an error naming its source, and the later item is skipped; nothing is overridden silently. Inventory slots hold indices into this list for the session only.

Each `DA_Items` entry becomes an `FFoundationItemDefinition`:

| 26.3 data | Definition |
|---|---|
| `max_stack_size` | `MaxStack` |
| `max_damage` | `MaxDurability` |
| attack totals (player base 1 and 4 plus the modifiers; no modifiers: 1 and 4) | `AttackDamage`, `AttacksPerSecond` |
| `tool.default_mining_speed` | `DefaultMiningSpeed` |
| `tool.rules` | `MiningRules`, in order |
| `tool.damage_per_block` (no tool component: 0) | `DurabilityPerBlock` |
| `weapon.item_damage_per_attack` (no weapon component: 0) | `DurabilityPerHit` |
| `weapon.disable_blocking_for_seconds` (no weapon component: 0) | `DisableBlockingSeconds` (data only until shields exist) |
| item tags | `Tags` (`Item.*`) |

**Tool rules.** The first matching rule that states a speed sets the speed; the first matching rule that states `correct_for_drops` decides the drop. A wrong-tier pickaxe keeps its speed and loses the drop (iron on obsidian: speed 6, no drop). `DA_Items` keeps each rule's selector verbatim and the `Block.*` tag a tag selector names (`#minecraft:mineable/pickaxe` is `Block.Mineable.Pickaxe`, `#minecraft:incorrect_for_iron_tool` is `Block.IncorrectForTool.Iron`). A tag is registered only when an imported block carries it. A rule whose tag is not registered (`incorrect_for_diamond_tool` and `incorrect_for_netherite_tool` are empty in 26.3) or that names a single block (the swords' `minecraft:cobweb`, which is not imported) has no tags and matches nothing. `.Rules` fails if such a rule names an imported block, so importing cobweb later means adding block matching. The swords' `#sword_instantly_mines` matches bamboo.

## Mining (items S5)

The authority mines by the 26.3 rules (minecraft.wiki "Breaking"), in the Playground and the generated worlds alike:

- **Speed and drops:** the held item's first matching rule that states a speed, else its default (the hand's 1); efficiency, haste, fatigue and break speed are neutral extension points; x0.2 with the eyes in water and x0.2 off the ground. The block drops when it needs no correct tool, or the first matching rule that states `correct_for_drops` says true (`FFoundationAuthority::CanHarvest`). d = speed / hardness / (30 if it drops, else 100).
- **Steps:** hardness -1 never breaks. Hardness 0, or a first step that completes the break, takes the instant path, with no delay after it in survival. Otherwise each step's `MineContinue` adds d until the progress reaches 1 within `CompletionTolerance` (1e-6, `FFoundationRules::CompletesBreak`), and a 5-step delay (`FFoundationInteraction::MiningDelaySteps`) passes before the next break accumulates.
- **The exact table:** the step counts equal `facts/break_times.json`'s exact ticks on all 22,248 entries of the imported blocks (`Unnamed.Foundation.Mining.Tiers`). 17,305 of the 19,288 progressive entries are whole-inverse (1 / d is a whole number). In double precision their progress lands within 4e-8 of 1, so the tolerance completes them on the exact tick, and every other entry is at least 4e-4 short of 1 one step before its last, so the tolerance never shortens one. 27 entries have d = 1 exactly (an iron hoe on leaves, an iron shovel on snow, a golden pickaxe on netherrack, an iron axe on mushroom blocks and vines): the block's single-precision hardness (0.2) leaves d at 0.99999998, and the tolerance puts them on the instant path, as the table and the game's single-precision 6 / 0.2 = 30 have them.
- **Creative** (wiki "Creative"): every block breaks at once, bedrock included, without drops or wear. Holding attack breaks one every 6 steps (the 5-step delay, then the next start); a fresh click breaks at once. An item whose `can_destroy_blocks_in_creative` is false (the swords) breaks nothing (reason `CreativeCannotBreak`), and neither do the spears: `FFoundationRules::CreativeNoBreakTags` holds `Item.Spears`, from the wiki's "Breaking" and "Creative" pages, because 26.3 gives spears no tool component. That rule is not yet black-box verified; clearing the container (one line in `BuildRules`) follows the data alone.
- **Wear (items S6):** with tool wear on (the finite fixture, survival worlds), breaking a block of hardness above 0 costs the tool's `damage_per_block` (1, the swords 2, the spears none: no tool component) and an accepted hit the weapon's `item_damage_per_attack` (2 for pickaxes, axes, shovels and hoes, 1 for swords and spears); an instant block (hardness 0) and an ignored hit cost nothing, and nothing wears in creative. The last point breaks the item once (`ToolBroke`). A creative write keeps the stack's damage (`FFoundationCommand::CreativeDamage`, from the creative screen's stack), and the authority refuses damage outside 0 to the max damage (reason `InvalidDamage`; an item that never wears takes only 0).
- **Known issues:** the post-break delay is 5 steps, then the next start; the wiki says 6 ticks. Whether the game's single-precision steps keep the exact ticks is open: summed in single precision, the bare hand on oak planks or a log takes 61 ticks against the exact 60, and stone 151 against 150, while a wooden pickaxe on deepslate stays at 45. Probe P5 settles both. Blocks without a loot table, and the blocks whose table is skipped (see "Loot"), keep the provisional "drops itself" rule.

## Loot (items S5b, loot steps 2a and 2b)

A survival break that may harvest the block (`CanHarvest`) rolls the block's 26.3 loot table, when it has one (minecraft.wiki "Loot table", "Predicate", "Item modifier"):

- **Which blocks:** with `foundation.Loot.AllBlocks 1` (the default), every imported block whose table is attached: 602 of the 616 imported blocks have a table, and since loot step 2b all 602 roll it (the 14 without one are bedrock, the wall torch, the three command blocks, the structure block, the jigsaw, the two test blocks and the five coral wall fans). They come from `loot_tables.json` through `DA_Items`, in the reference's order: the 18 ores first (items S5b), then the others in `block_manifest.json`'s order. `UFoundationItemAssets::AddLoot` (called by `BuildRules`) resolves each table's items, predicates and condition kinds into `FFoundationRules::LootTables` (by block id) and `LootPredicates` (`tool/can_silk_touch`, `tool/can_shear`). With `foundation.Loot.AllBlocks 0` only the 18 ore tables roll (`FoundationLoot::LegacyTables`), as items S5b did, and every other block drops itself.
- **Skipped tables:** a table naming an item the project does not define, or a condition kind the runtime lacks, is skipped (logged), and its block keeps "drops itself". None is skipped since loot step 2b, which added the 23 items the 31 skipped tables named: the 11 leaves (oak, spruce, birch, jungle, acacia, cherry, dark oak, pale oak and the three poplars, which share the poplar sapling) drop saplings, sticks and (oak, dark oak) apples; gravel flint (10%); short grass, tall grass, fern and large fern wheat seeds (1 in 8); snow and the snow block snowballs; clay clay balls; glowstone glowstone dust; melon melon slices; sea lantern prismarine crystals; cocoa cocoa beans; the sweet berry bush sweet berries; cave vines and their plant glow berries; the amethyst cluster amethyst shards; the bookshelf books; the creaking heart resin clumps; gilded blackstone and nether gold ore gold nuggets.
- **What changes:** stone gives cobblestone and deepslate cobbled deepslate (with a pickaxe; by hand nothing, since the hand cannot harvest them); the grass block, podzol and mycelium give dirt; glass, stained glass, ice and the other Silk-Touch-or-shears blocks give nothing, and so do budding amethyst, the suspicious blocks and the other empty tables; a double slab gives 2 through its table. Stone itself now comes only from smelting cobblestone (or, later, Silk Touch), and smooth stone from smelting stone. Blocks whose table drops the block itself behave as before.
- **Evaluation** (`FoundationLoot`): each pool's single entry is flattened into ordered candidates, and the first whose conditions all pass drops (the wiki's `alternatives`). A pool may have conditions of its own, checked once before its rolls. Conditions are the named predicates and a closed set of kinds, kept per table as nodes (`FFoundationLootCondition`): `survives_explosion` (true: nothing explodes), `match_block` (the broken block and its state, which `BreakBlock` passes in `FFoundationLootContext`), `any_of`, `all_of`, `inverted`, `table_bonus` (a random fraction below the chance at the Fortune level, 0), `random_chance`, `match_tool` (the item list, a tag resolved by the reference), `entity_properties` (the player) and `location_check` (loot step 2b: the block and state at an offset from the broken cell, through `FFoundationLootContext::GetBlockAt`; the jar's x, y, z is the cell's X, Z, Y). `BreakBlock` rolls before the block is removed, so breaking either half of tall grass or large fern sees the other half and rolls once; the other half then pops without drops. Modifiers apply in order to a count of 1, the candidate's, then the pool's, then the table's, each when its own conditions pass: `set_count` (a whole uniform or constant, or added with `add`), `apply_bonus` (Fortune at level 0: no change), `limit_count`, `explosion_decay` (data until explosions exist), and `copy_components` and `copy_state` (data: stacks carry no components yet). An item at a count of 0 or less is not dropped. The ore form of S5b (a count range, the bonus, the decay) becomes the same modifiers, so the ores roll as before.
- **Randomness:** each roll is an `FRandomStream` seeded by `FoundationLoot::MakeSeed(Rules.LootSeed, Cell, Breaks)`, a pure function of the rules' loot seed (0 until a world's seed is wired in), the cell and the authority's break count before the break. Chance conditions draw from the same stream. A refused break rolls the same again.
- **Inventory:** with `foundation.Items.Entities 1` (the default since items S8a) the rolled stacks drop into the world as item entities (below), and a full inventory no longer refuses the break. With 0, every rolled stack must fit, or the break is refused (`InventoryFull`) and the block stays, as before. A roll that yields nothing still breaks the block. `FFoundationResult::Drops` lists what a break dropped or returned.
- **Known issues:** the loot seed is not yet the world's seed. Drop counts are checked against the data and the wiki, not yet black-box (optional probe P8: a headless 26.3 server's `/loot ... mine`). Silk Touch, Fortune, shears and explosions are data only. The wiki's Silk Touch page gives lapis 4 to 8, while its Lapis and Fortune pages and the data give 4 to 9; the project follows the data.

## Item entities (items S8a)

A survival break's loot pops out of the block as item entities, which fall, rest on the ground and are pulled into the inventory when the player walks over them (scout AC's plan step 3; `foundation.Items.Entities`, default 1; 0 returns the loot straight to the inventory as before, and drops already in the world stay until picked up).

- **Where they live:** the authority owns them (`FFoundationAuthority::GetItemEntities`, plain data in `FoundationItemEntities.h`) and steps them in `Step()`, once per reference step: the targets' cooldowns, then every drop's motion and pickup delay, then each live player's pickups. `Options.bItemEntities` switches `BreakBlock`; the pawn copies the console variable in before each step, and tests set it themselves (it defaults to off in the struct, so a test-built authority keeps the inventory path). `SpawnItem` adds one (the tests, the probes, and the Q throw). `Reset` clears them. Positions are cm from the block world's origin, so world rebasing never moves them.
- **Spawn:** each rolled stack, split at its max stack, at the cell's centre lowered by half the box, moved up to 0.25 blocks on each axis, at up to 0.1 blocks per tick sideways and 0.2 up (`FoundationLoot::MakeSeed` of the loot seed's complement, the cell and the break count: deterministic, apart from the roll's stream). The look's phase comes from the drop's id.
- **Motion** (`FoundationItemEntities::Move`): gravity 0.04 blocks per tick squared, then the move, clipped against the collision the player moves against (`FFoundationSimulation::Clip`, vertical first), a blocked axis stopping, then the drag 0.98 on every axis and, on the ground, the block friction 0.6 sideways. The terminal speed is 1.96 blocks per tick. The collision is the authority's `GatherCollision` hook, which the Playground and the generated world set to their own query: the lab's fixtures and the blocks, and in a generated world ungenerated columns as solid, so a drop stops at their face as the player does. Unset, the block world's boxes and the statics.
- **Streaming:** a drop whose column is not loaded (`IFoundationBlockStorage::IsLoaded`) is frozen: no motion, age, pickup delay or pickup, and not drawn, until the column is back (vanilla's entities do not tick in an unloaded chunk). Below the world's lowest cell minus 64 a drop vanishes.
- **Pickup:** after a 10-step delay (block drops), a live player picks up every drop whose 0.25-block box overlaps the body grown by a block sideways and half a block up and down (strictly: touching does not count), oldest first, through `FFoundationInventory::Add` without touching the merged stacks' own revisions (only the inventory's), so a break in progress with the held stack goes on, as vanilla's compares the item, not the count: only what fits transfers and the rest stays in the world. Each pickup adds a `PickedUp` event (player, drop id, item, count, location, whether the whole stack went). The earliest pickup is the 10th step after the spawn, since drops step before pickups.
- **Look** (`FFoundationItemEntityView`, owned by the interaction view): each drop within 64 blocks of the camera (at most 256, nearest first) is drawn with the held item's meshes in its model's `ground` display, between the last two reference steps: a block item as its block's default state on the block materials (`block/block.json`'s ground: scale 0.25, up 3 pixels), any other item as its extruded sprite (the item models' ground: scale 0.5, up 2 pixels) on `M_HeldItem` without the hand's glow, lit by the scene. It is lifted by 0.25 x its ground scale, bobs 0.1 x sin(t / 10 + phase) + 0.1 blocks and spins t / 20 + phase radians. A whole stack picked up by the local player flies to the player's centre over 3 steps. Every pickup plays `entity.item.pickup` at the drop through `FFoundationBreakEffects::PlayEvent` (the sound reference; `foundation.Sound.Events`), at vanilla's call-site volume 0.2 and a pitch from 1.6 to 3.4 (drawn uniformly, provisional).
- **Sources:** minecraft.wiki "Item (entity)" (the box, the 10-tick delay, the pickup box, partial pickups, vanishing below the world) and "Entity", Motion table (items: gravity 0.04, drag 0.98 both ways, terminal velocity 1.96). **Provisional** until probe P3 measures a 26.3 client: the order within a step beyond acceleration before drag, the ground friction (the wiki's default block friction is stated for living entities only), the spawn spread and speed (facts section 2, "commonly cited"), the strict pickup edge, and the look (lift, bob, spin, the 3-step fly).
- **Throw, merge, despawn (items S8b, plan step 4; the same switch):** Q throws one item of the selected stack and Ctrl+Q the whole stack (`FFoundationAuthority::Drop`, the `Drop` command's `bWholeStack`), in survival and creative alike (vanilla's creative Q takes from the stack too); an empty hand is refused (`NoSupply`), and with the switch at 0 Drop is refused (`DropDeferred`) as before. A thrown stack keeps its damage (`FFoundationItemEntity::Damage`), and the pickup gives it back (`FFoundationInventory::Add`'s `Damage`, default 0, merging only into stacks of the same damage). It has a 40-tick pickup delay, so the earliest pickup is the 40th step. Every 40 steps of its own age, a live item takes in same-item, same-damage stacks whose box overlaps its box grown 0.5 blocks sideways and 0.25 up and down (strictly), up to the max stack (`MergeItemEntities`, after the motion and before the pickups; frozen items take no part). An item despawns when its age reaches 6,000 steps (5 minutes; the age does not count while frozen), before that step's pickups (vanilla's order there is unverified). A stack draws 1 copy, then 2, 3, 4 and 5 from 2, 17, 33 and 49 items (`GetCopies`), each after the first moved up to 0.15 blocks on each axis (half that for a flat sprite), fixed by the entity. Sourced (minecraft.wiki "Item (entity)"): the 40-tick delay, the 6,000-tick despawn, the merge box and its 40-tick cadence, the copy thresholds. **Provisional** (code-only values, not on the wiki; P3): the throw (from 0.3 blocks below the eye, 0.3 blocks per tick along the look plus 0.1 up, plus up to 0.02 sideways in a random direction and up to 0.1 up or down), the merge cadence's base (the item's age; vanilla checks moving items more often, not modelled), the merge direction (the smaller stack into the larger, into the seeker on a tie; the result keeps the longer delay and the younger age, so a merge restarts the older stack's despawn clock and moves its merge phase) and the copies' offsets.
- **Known issues:** drops sink through water (vanilla floats them) and are not destroyed by lava, fire or cactus; a block placed over a drop does not push it out (S8a-b, left: more than a small change); drops are lit by the scene, not the light level at their cell (the cave capture is the look call); the sprite arrays have no mips (S4-g), so small drops may shimmer; the opt-in mine probe (`CaptureVoxel.ps1 -MineProbe`) leaves its drop in the world, so its hotbar line shows the pickaxe only.

## Inventory and container clicks (survival step 5a)

The player's inventory is vanilla's: the hotbar, 27 main slots, 4 armor slots and the offhand (`foundation.Inventory.Full`, default 1; 0 is the lab inventory, the hotbar and offhand only, as before).

- **Numbering** (`FFoundationInventory`, `FoundationItems.h`): vanilla's Inventory numbers, 0-8 the hotbar, 9-35 `Main`, 36-39 `Armor` (feet, legs, chest, head), 40 the offhand. `GetSlot` and `SetSlot` take them; with the switch at 0 `GetSlot` refuses 9-39. `SetCreativeSlot` uses the same numbers (the offhand moved from 9 to 40). `Options.bFullInventory` switches it; the pawn copies the console variable in before each step and the authority sets `Inventory.bFull` from it on each command and pickup step, so a test-built authority keeps the lab inventory unless it sets the option.
- **Fill order** (`Add`, `GetSpaceFor`; item pickups, loot returns and the cursor's return on close): merges into the selected stack, the offhand, then slots 0-35 in order; then the first empty slot of 0-35, hotbar before main. The offhand never takes a new stack. Source: minecraft.wiki "Inventory"; **provisional** until probe P3 (a vanilla client run, Jesus's go).
- **Clicks** (`FFoundationContainerMenu`, `FoundationContainer.h`, UObject-free): one container screen's slots and vanilla's click types over an inventory, with the cursor stack (`Inventory.Carried`) and a drag (`Inventory.QuickCraft`) kept on the inventory. Container 0 is the player's menu in vanilla's InventoryMenu numbers: 0-4 the crafting result and grid (refused until survival step 6), 5-8 the armor head to feet, 9-35 main, 36-44 the hotbar, 45 the offhand, -999 outside the window. A moved whole stack keeps its instance id; a split part is a new instance; a stack whose count changed bumps its own revision.
  - PICKUP: left takes or places all, right takes the larger half or places one; a different item swaps; outside the window the cursor stack (left) or one of it (right) is thrown.
  - QUICK_MOVE (shift): armor goes to main then the hotbar; a wearable item to its empty armor slot, an offhand item to an empty offhand; otherwise hotbar to main, main to hotbar, and the offhand to main then the hotbar, merging first, then empty slots.
  - SWAP: buttons 0-8 (the number keys) and 40 (F). CLONE (middle, creative only): a full stack on an empty cursor. THROW (Q, Ctrl+Q): one or the stack, only with an empty cursor.
  - QUICK_CRAFT (a drag): button = phase (0 start, 1 slot, 2 end) | type << 2 (0 left, an even split with the remainder kept; 1 right, one each; 2 middle, creative, full stacks without spending the cursor). Never more slots than items; one slot is a plain click; any other click ends a drag and does nothing else.
  - PICKUP_ALL (double-click on an empty slot): matching stacks into the cursor up to a full stack, non-full stacks first, from the first slot (left) or the last.
  - Armor slots take only items whose `FFoundationItemDefinition::Equipment` is their slot, one at a time. No item has one yet (no reference item has `minecraft:equippable`); armor (survival step 19a) fills it.
- **Commands:** `ContainerClick` (`ContainerId`, `Slot`, `Button`, `ClickType`) runs the menu on a copy and commits it unless the click throws: throwing waits for survival step 4, so a throw is refused with `DropDeferred` and nothing changes. `ContainerClose` puts the cursor stack back (`FFoundationInventory::Return`: Add's order, merging only into the same item and damage, the rest keeping its identity in a free slot); if it does not fit it is refused the same way. The client side is `FFoundationInteraction::ContainerClick` and `ContainerClose`. Only container 0 exists.
- **The creative screen** (`FHudCreativeModel`) runs the same menu on a copy of the 41 slots for the hotbar, main, armor and offhand, then sends each changed slot as `SetCreativeSlot`, as vanilla's creative screen does; shift is QUICK_MOVE in the survival tab and still deletes in the picker tabs; middle clicks clone. With the switch at 0 its main and armor slots draw empty and do nothing. Drag and double-click gestures arrive with the survival screen (step 5b).
- **Saved data:** none; the inventory lives in the authority for the session.

## Eating (step 10)

Hold use with food to eat it over 1.6 s (scout AC's plan step 10; `foundation.Items.Use`, default 1; 0 lets food pass, as before; axe stripping and buckets, steps 14 and 17, will hang off the same switch).

- **Data:** `FFoundationItemDefinition::GetConsumable` gives the definition's own `Consumable` (tests author one), else `FoundationConsumables::FindReference` by id: a native table of `items.json`'s six foods (apple 4 and 2.4, bread 5 and 6.0, cooked beef 8 and 12.8, melon slice 2 and 1.2, sweet and glow berries 2 and 0.4), all with `consumable: {}`, so 1.6 s, 32 ticks. A test pins the table against `items.json` row by row. It is a table and not a `DA_Items` field because the item asset is a hash-guarded binary that other lanes may touch before the final merge; moving it into the importer is a later migration (known issue).
- **Commands** (`FFoundationAuthority`): `UseItemStart` checks the hand (as every hand command), passes without the switch or a consumable, refuses at full hunger (`NotHungry`, wiki "Food"; an invulnerable mode may always eat, provisional), and records the use on the player (`FFoundationItemUse`: hand, stack instance, item, ticks, duration). `UseItemContinue` advances it one tick per reference step (a second one in the same step is refused `StepLimit`); at the duration it calls `FFoundationVitals::Eat` (saturation capped at the new hunger), consumes one from the stack (not with infinite supply) and returns `bAte`. `UseItemRelease` cancels (`Released`); nothing is consumed before the end. A slot change, a swap, death, another stack in the hand (by instance, so a pickup into the stack keeps the meal going) or a step without a continue (`Step()` drops it) also cancel.
- **Client** (`FFoundationInteraction`): per hand, the target's use (`UseOn`/`UseEntity`) first, then, if it passed and the hand holds a consumable, `UseItemStart`, in the air too (switch 0 keeps the old early return on a miss). While eating it sends a continue each step and a release when use is let go; still holding after a meal, the next starts after the held repeat. Attack does nothing while eating.
- **Slowdown:** while the authority's use is active the pawn sets `bItemSlows`; the simulation scales the move input by 0.2 (facts section 5, unverified) and, as before, no sprint starts.
- **Presentation:** events `Eating` (every 4th tick from the 8th: the project's own cadence, provisional) and `Ate` (with the nutrition). The interaction view plays `entity.generic.eat` on each (volume 0.5-1.0, pitch 0.8-1.2) and `entity.player.burp` after the last (0.5, 0.9-1.0), through `PlayEvent`; the volumes and pitches are provisional, unverified. The held main-hand item eases 0.1 s into an eating pose (toward the mouth, turned in) and bobs once per 4 ticks: the project's own motion, provisional until a vanilla capture. The event log shows "ate apple".
- **Known issues:** no eat particles (the break chips draw block textures only; item-sprite crumbs need their own material path). An offhand meal has no motion (the offhand is not drawn). The 20% slowdown, the sound values, the effect cadence, the creative exception and the motion wait on a vanilla capture (probe pending Jesus's go). Vanilla's always-edible foods (golden apples, chorus fruit, and others) are not among the project's items, so there is no exception list.

## Combat (items S7)

The authority's `Attack` follows the wiki's melee rules ("Damage", "Sweep attack", "Knockback"):

- **Cooldown:** the held item's attack speed (`AttacksPerSecond`, set by the interaction's equipment sync) gives a full charge in 20 / speed ticks. Damage is the item's `AttackDamage` x (0.2 + 0.8 s^2), s = (t + 0.5) / (20 / speed) clamped to 1, t the ticks since the last swing or item switch; another stack of the same item keeps the charge.
- **The 84.8% gate:** a charge above 0.9 (`FFoundationRules::CriticalStrength`) makes an attack special. Sprinting, it is a sprint-knockback attack: extra knockback, and the attacker's sprint ends (`FFoundationInteraction::bStopSprint`, which the pawn clears). Else falling off the ground (not climbing, in water, riding or sprinting), a critical (x1.5). Else it may sweep.
- **Sweep:** a sword (`FFoundationRules::SweepItemTags`: `Item.Swords`, from `BuildRules`) on the ground, after a landed hit, when the attack is neither a critical nor a sprint-knockback attack and the player moved at most 10 cm over the last step (`FFoundationPlayerFacts::StepMovedCm` against `SweepMaxMoveCm`, the movement_speed attribute's 0.1 blocks per tick; so a walking player does not sweep). Every live target whose box meets the primary's grown 100 cm across and 25 cm up and down, and whose position (its box's bottom centre) lies within 3 blocks of the player's feet, takes 1 (`SweepDamage`, plus `SweepingDamageRatio`, Sweeping Edge's extension point at 0, x the hit's cooldown-scaled damage: the wiki's base melee damage, which the cooldown scales) through its own damage cooldown, with a hit event marked `bSweep`. Wear and exhaustion count once per attack.
- **Knockback, as data:** a landed hit outside the target's hurt window knocks it back (`bKnockback` on the result and the hit event); inside the window a bigger hit lands only the difference, without knockback. A landed sprint-knockback attack is flagged (`bSprintKnockback`), inside the window too. Swept targets are knocked back at the wiki's 0.4 blocks per tick (`SweepKnockback`). The training targets are anchored, so nothing moves yet.
- **Shield-disable, as data:** `FFoundationItemDefinition::DisableBlockingSeconds` carries `weapon.disable_blocking_for_seconds` (the 7 axes 5 s, every other item 0). Nothing blocks yet.
- **Known issues:** the wiki gives no base melee knockback strength, direction or velocity formula (probe P7, with the first movable entity). At exactly 0.9 (the bare hand at 4 ticks; the wooden, stone and copper axes at 22) the project lands no critical or sweep, while the wiki says "84.8% or above" (probe P5). Whether walking never sweeps, and a sweep's wear, are P5's too. Spears' melee (minimum charge 1, reach 2 to 4.5 blocks, no criticals or sprint-knockback, the piercing jab) waits for a spear session; until then they attack like any item.
