# Survival step 7: the crafting table (record)

Lane `feature/survival-containers` (worktree `C:\dev\projects\Unnamed-inv`), track T1 Containers. Behaviour is in `Docs/Items.md`, "The crafting table and block use (survival step 7)", with step 6's "Crafting" updated for review 10.

## 1. What was built

- **Block use** (`foundation.Blocks.Use`, default 1; 0 right-click always places): `FFoundationAuthority::RegisterBlockUse(FName BlockId, FBlockUse)` is the generic hook (block id to handler) that T5's doors, buttons and levers register into. `UseOn` runs it as branch 1b: after a static's lab interaction, before stripping and placing, main hand only, skipped by a crouching player holding something (the existing `bBypass`). The crafting table is the one built-in handler. The client preview mirrors it (`HasBlockUse`).
- **A second menu layout**: `FFoundationMenuLayout` (one row per `EFoundationMenuKind`) replaces the hard-coded ranges in `FFoundationContainerMenu`; the player's menu keeps step 5b's numbering slot by slot (`.Layout` checks it). The crafting table's menu is 0 the result, 1-9 the 3x3, 10-36 main, 37-45 hotbar. Its grid is `FFoundationPlayer::OpenMenu.Grid` (the screen's, never saved).
- **Open, click, close**: the table's use opens container 1-100 (wrapping) and emits `ContainerOpened`; the pawn opens the screen (`UFoundationPanels::OpenContainerScreen`, the inventory's screen is now the same function with container 0). Clicks carry the id; stale ids and a broken table are refused `InvalidSlot`. Close returns the cursor, the 3x3, then the 2x2.
- **The screen**: `SHudContainerScreen` and `FHudContainerModel` take a `Kind`; the crafting table draws `crafting_table.png` (a new asset of our own, `/Game/Gui/Container/gui/container/crafting_table`, `ImportContainerGui.py`, `Docs/StandIns.md` row) with the value report's slot positions.
- **Codex 5b finding 4** and **review 10** (`C:\dev\tools\shift-managers\survival\codex\reviews\10-T1-6\report.md`): (1) `foundation.Crafting 0` makes the grid and result inert, the grid's items still returned on close; (2) thumb mouse buttons act as their bindings over the screen; (3) `.Chain`'s right click takes a count-4 result; (4) a result slot is exempt from the double-click (each click crafts; taken first, at the PM's priority); (5) and 5b #4: the client copies `foundation.Inventory.Full` and `foundation.Crafting` into the authority on every container click and close.
- **Found by the tour**: the controller's event-name table (`AFoundationController::NoteInteraction`) is indexed by event kind; its `static_assert` named the last kind, so a new kind read past the array (a crash in the tour run `Runtime-20261014-195254`). It now names `ContainerOpened` and has its "opened" entry.

## 2. Decisions

- One menu class with a layout table (SM, Q1); handlers registered by block id on the authority (SM, Q2), not a DA_Blocks flag (no lock needed).
- An empty-handed sneak opens the table (vanilla: the bypass needs an item); the off hand never uses a block.
- A close without room: after merging feature/survival 229528f (T2's items fixes), the 3x3's leftovers go through T2's throw path with the 2x2's (`Throw`, as Q); with `foundation.Items.Entities 0` the close is refused, the grid stays with the open menu and a reopen carries it over rather than lose it.
- No auto-close when the table breaks or the player walks away: clicks are refused instead (known issue).
- A key or thumb button bound to two screen actions fires both (vanilla's per-action checks; kept).
