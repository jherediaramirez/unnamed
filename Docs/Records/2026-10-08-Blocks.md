# Blocks - October 8, 2026

The Playground now has every full-cube block and slab of Minecraft Java 26.3 (529 blocks), plus air and static water. It uses the 26.3 protocol and state ids, textures, render layers, tints, animation and placement rules. Blocks are picked from a reproduction of the 26.3 creative inventory, and a block gallery shows every block and state. The dummy block is retired. How it works: [Blocks](../Blocks.md). Brief: [Block_System_Prompt.md](../Block_System_Prompt.md).

## What changed

- **Reference:** `Reference/minecraft-blocks-26.3/` holds the jar files byte for byte, the manifests and the server facts dumped by `tools/FactsDump.java`. It is generated by `tools/build_reference.py`, which refuses to run over existing output, and checked by `tools/verify_reference.py`. `Docs/MinecraftBlockReference.md` points at it.
- **Registry (C++):**
  - `FoundationBlockAssets.h` defines the `DA_Blocks` asset type.
  - `FoundationBlockRegistry.*` is the runtime registry: lookups, the state codec, shapes, faces and animation frames.
  - `FoundationBlockPlacement.*` holds the vanilla `getStateForPlacement` families.
  - `FoundationBlockMeshes.*` and `FoundationBlockTextureTable.*` build the runtime meshes and the animation table.
  - `FoundationBlockImport.*` and `FoundationBlockMipmaps.*` are the editor import helpers; the mipmaps are a port of vanilla `MipmapGenerator`.
  - `FFoundationBlockState` is now a 26.3 state id. `FFoundationBlockWorld` holds a shared registry, and `FoundationBlocks.h` keeps project-block authoring only.
- **Authority:**
  - Placement resolves the state through the vanilla rules.
  - Slabs merge to double, and a double slab drops 2.
  - Mining uses the 26.3 hardness and tool tags.
  - New command `SetCreativeSlot`, gated by `FFoundationLabOptions::bCreativeInventory`.
- **Presentation:**
  - `UFoundationInteractionView` draws one instanced mesh per section, mesh and render layer, with nine floats of per-instance data.
  - Four materials sample the texture arrays.
  - Water has its own material and heights.
  - The held block, the preview and the outline use the state's shape and textures.
- **Creative inventory:** `Hud/HudCreative.*` holds the pure model and the 3D icon quads; `Hud/HudCreativeScreen.*` is the Slate screen. In the Playground, E opens it. The in-game hotbar draws block items with the same 3D icons.
- **Playground:**
  - The starter blocks are stone, and the loadout is `stone`, the practice pickaxe and the practice sword.
  - The block gallery has the showcase rows, every block in registry order and every state in state-id order.
- **Settings:** `UFoundationInteractionSettings` holds only project blocks (none by default), the tools, presets and loadout. Block items come from the registry (`AddBlockItems`).
- **Scripts and config:**
  - `Scripts/Editor/BlockImportData.py`, `ImportBlocks.py` and `CreateBlockMaterials.py`.
  - `ProjectPaths.block_asset()`.
  - `Config/Tags/MinecraftBlockTags.ini` (194 tags).
  - `/Game/Blocks` added to `DirectoriesToAlwaysCook`.
  - `UUnnamedProjectSettings::BlockRoot`.
- **Tests:**
  - New `Unnamed.Foundation.Blocks.{Registry, Codec, Faces, Textures, Placement, Shapes}` and `Unnamed.Hud.Creative.{Tabs, Clicks, Authority}`.
  - The interaction tests use a stand-in `lab_block`.
  - The probes expect stone. The tour adds gallery shots 09-19 and creative shots 20-23.

## Decisions

- **Item id = block id.** Made by the user ("whatever you think it's best"); this was the recommended option. It matches Minecraft and needs no mapping table, and the item ids are saved ids from now on.
- **Dummy block retired.** Made by the user. `dummy_block` and `dummy_block_item` are never reused. Stone replaces the dummy block in the stations, the loadout and the probes.
- **Block picker = the vanilla creative inventory.** Made by the user: a 1:1 reproduction rather than new UI, with vanilla art, layout, tab contents and click rules.
- **Registry asset.** One generated data asset (`DA_Blocks`) instead of a DataTable or config. The registry is too large for config, and an asset cooks and loads with the textures it indexes. Project-authored blocks stay in settings and append after the imported ids.
- **Project ids** start after the vanilla ranges (protocol 1286, state 35723), so imported ids stay exact.
- **Icons:** 3D GUI icons follow the vanilla `block` item display transform: rotate x 30, rotate y 225, scale 0.625. The face shades (1.0, 0.68, 0.44) were measured from a 26.3 screenshot, not derived from the lighting code.
- **Drops** are "drops itself" (a double slab drops 2). This rule is provisional and clearly labelled, pending loot tables.

## Gaps

- **No neighbor updates:** snowy grass and leaf distance are set at placement only and do not change when neighbors change.
- **Waterlogging is inert:** the property exists and placement sets it to false.
- **No water behavior:** no flow, no swimming, and players cannot place water.
  - Water blocks exist only in the gallery.
  - The station and course water are still the lab's water volumes. `AFoundationLab::IsInWater` checks only those, so standing in a water block does not count as being in water for air or mining.
- **Rendering:**
  - No face culling between instances and no translucency sorting.
  - Animation blends in linear rather than sRGB space.
  - The destroy-stage textures are unused; the old crack overlay is hidden on textured blocks.
  - Random-rotation variants use their first entry.
  - The water material is heavy: 1,929 pixel-shader instructions.
- **Creative inventory:**
  - No player model on the inventory tab and no chest icon.
  - Saved Hotbars is empty.
  - The practice tools borrow the diamond pickaxe and netherite sword sprites.
  - `#` search uses block tags, not item tags.
- **Out of scope as briefed:** non-cube blocks, loot tables, and per-biome tints (plains values everywhere).

## Seams

- **Chunk loader:**
  - `IFoundationBlockStorage` is the storage interface; `FFoundationSectionStorage` stores 16³ sparse sections.
  - Cells already hold 16-bit state ids, ready for paletted sections.
  - Saves use `FFoundationBlockRegistry::Save`/`Load` (`{id, properties}`).
  - The view batches by section, so a chunk can rebuild only its own section.
- **Water behavior:**
  - `FFoundationFluid` (`GetFluid`, `GetHeight`) already gives level and height per state.
  - The `waterlogged` property is in every slab state.
  - Flow logic can set states through the authority like any other change.
- **Neighbor updates:** `FoundationBlockPlacement::GetStateForPlacement` already computes snowy and leaf distance. An update pass can reuse it when a neighbor changes.
